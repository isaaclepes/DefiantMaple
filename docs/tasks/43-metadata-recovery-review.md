## Design clearance criteria

- A consistent schema-6 SQLite snapshot is verified from closed bytes, with exact declarations, integrity, foreign keys, orphan provenance, package digest, explicit omissions, and bounded inspection before publishing or restoring. A separate writer may cause incremental backup retries; the operation needs finite busy handling, a deadline, cancellation checks, and truthful refusal or uncertain results.
- Package and restored-catalog publication must be no-overwrite even when a target appears during work. Define supported local placement, root/cache/source-tree containment, symlink/reparse-point handling, same-volume staging, file and directory sync semantics by platform, cleanup ownership, and the exact meaning of “verified” versus power-loss durability. Never replace the live catalog or an earlier recovery point.
- The isolated restored catalog must preserve stable asset IDs/revisions and all schema-6 metadata, with only enumerated activation-state differences. A persistent pending marker must cover source-backed and `source_id`-NULL assets. Unknown marker values fail closed in the current runtime. Original media and external actions remain blocked while pending; after explicit mapping review, marker clearing is atomic, sources remain disabled until individually enabled, and catalogs containing standalone restored assets are not activated by this narrow slice.
- Guard the worker that actually opens an original, not only the visible Qt control or captured gallery row. Current paths include Core thumbnail generation, external-action pre-probe and pre-dispatch checks, Qt inspector and comparison workers, and scan/index/CLI entry points. Cache-only metadata and derived-preview browsing remains available. Ordinary enabled-but-paused source behavior remains unchanged.
- The user flow must make the metadata-only omissions, unresolved roots, pending state, old-build compatibility limitation, and refused/uncertain outcomes visible. It must not auto-open or activate a restored target or retarget an existing gallery. Qt work stays off the GUI thread and owns worker shutdown.
- The design and acceptance documents must retain FR-LIB-005 Partial and FR-RECOVERY-001–007 Not Started until evidence supports a later narrowly scoped tracker update. No stable library ID, scheduled snapshots, portable export, broad writer broker, media-inclusive backup, or full recovery claim is inferred from this slice.

## Findings resolved in the reviewed design

1. `sources.enabled=0` and `health='paused'` do not guard all original access: external actions currently ignore `enabled`, paused health remains eligible, and standalone assets have no source row. A persistent restored-catalog guard plus per-source eligibility checks are necessary.
2. `prototypes/qt/preview.py::_decode_original` opens the path in a child from a captured asset dictionary and has no database argument. A UI-only eligibility check is stale. The design must require a fresh current-runtime admission check in that child before original open and describe the activation race boundary.
3. Existing schema-6 binaries ignore `PRAGMA application_id`. Retaining schema 6 is acceptable for this bounded milestone only with an explicit current-build-only guard claim and a prominent old-build warning; it is not cross-version protection. Direct SQLite readers are outside the application guarantee.
4. A no-overwrite publication primitive must be paired with supported-parent and containment rules. Checking a destination before a later rename is insufficient because another actor can create it in between. Any platform without the required primitive must refuse, and any unsupported directory-flush guarantee must be described as unproven rather than called durable.

The reviewed [design](../metadata-recovery-design.md) is SHA-256 `12e14b91116be0818dc211a5ff415bc062de9311c3b30ff85cdc3f022c0bb156`; [Task 41](41-metadata-recovery-implementation.md) is SHA-256 `61d0b2d57ef06e3f96d17b1c8b0d0247330d426cfed1da7552b0d37d0c7e322a`. These revisions explicitly require admission before `index_file` resolves or stats media, fresh catalog/asset admission inside the inspector child and comparison worker, and fail-closed checks at raw product SQLite openers. They define a complete captured root review, a transactional pending-marker clear only for linked-only catalogs, and a separate explicit Qt per-source enable action. The no-overwrite primitive, platform refusal paths, and current-build-only old-version caveat are stated. I checked in a disposable SQLite database that an `application_id` write inside `BEGIN IMMEDIATE` is rolled back with its transaction.

**Disposition:** Clear the frozen design for Core-first implementation, followed by a separate Qt integration gate. This clearance is for a schema-6, current-build, private-local metadata-only slice. It does not certify the storage adapters, worker limits, guard completeness, security against older binaries, power-loss durability on Windows, or any runtime/acceptance result. Before Qt or acceptance, review the Core implementation against every named guard and publication failure boundary. Task 42's protocol now includes generated cases for linked-only activation, standalone activation refusal, per-source enable without scan, pre-stat index refusal, and unknown-marker raw SQLite openers. Keep generated cross-platform evidence and independent final code/privacy review as separate gates. If either reviewed design document changes materially, repeat this design review against its new hash.
