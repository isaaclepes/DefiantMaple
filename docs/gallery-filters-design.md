# Gallery filters: immutable query and bounded Qt read design

Design gate for Tasks [38](tasks/38-gallery-filters-implementation.md)–[40](tasks/40-gallery-filters-review.md), 8 October 2026. This is a proposed runtime contract for independent review, not implementation or acceptance evidence. It preserves schema 6 and the merged PR20 runtime. The GUI path must satisfy the whole read gate below before new controls are connected; moving only Apply's count to a thread is insufficient.

## Product state and validation

Use one mutable **draft** in the controls and a frozen `GalleryQuery` for the **applied** view. The frozen value contains optional review state, source ID, media type, one canonical tag ID, one canonical entity ID, `RatingFilter`, `FavoriteFilter`, literal path text, optional exact duplicate digest, and optional manual collection ID. Collection ID is the base view/order, not an active facet. `GalleryQuery` also carries a closed order enum: ordinary library order `(assets.discovered_at, assets.asset_id)` or manual collection order `(members.position, assets.asset_id)`. Preserve the existing ascending SQLite ordering and tie break; no new sort control. All fields, including tag and entity, combine with `AND`.

The GUI constructs a candidate without mutating the applied value. Refuse nontext/unknown enum values, malformed rating/favorite values, unresolved picker text, selected IDs over 256 Unicode code points, and path text over **512 Unicode code points**. Path input is stripped as today; blank means no predicate. Reject path controls; picker text follows `metadata._name`'s existing control/whitespace rule. Never silently truncate either or treat a query-language-looking string as grammar. The path field is labeled **Literal path/filename text**: keep the current SQLite `LIKE` case behavior and escape backslash, `%`, and `_` before surrounding the bound value with `%`. The source/media/review values come from typed control data. The duplicate digest remains an exact bound string from the existing duplicate-group selection, with a 256-code-point request cap; do not impose a new hex-only rule on old model callers or generated fixtures.

Apply/Return share one operation: freeze and validate the *entire* draft, then submit one latest-pending generation. Validate the selected source/tag/entity/collection IDs in the same worker read snapshot that calculates count and page zero. A canonical record that exists but has no direct assignments is valid and can yield zero matches. A missing/deleted selected record is a visible **stale filter** refusal and leaves the previous applied view. Plain picker text without a selected canonical ID blocks Apply, even when no result matched. Alias selection stores the canonical ID, never alias text. Equal entity names display their category and canonical identity. No implicit descendant tags, OR lists, taxonomy edits, title/description search, or schema migration.

Ordinary Apply carries an explicitly selected duplicate digest forward; it cannot silently broaden the duplicate subview. **Clear filters** submits the all-facets-empty value, including no duplicate digest, while retaining the chosen manual collection and its order. Its label/status explains that the collection remains. A collection change submits a new base view with the current applied facets; it is distinct from clearing facets. Failed validation or read retains the previous applied value/count/pages, with a visible reason. Successful Apply atomically publishes the new count and first page, clears current index, multi-selection, detail and single/multi-action targets, and never selects row zero. Captured inspect/cache/comparison/external/curation dialogs retain their own stable IDs and existing drift/refusal checks.

## One predicate and one order

Build SQL solely from closed, typed fragments and bound values. The base is `assets`, with the existing collection-members join and `members.collection_id=?` only when a collection is chosen. Keep existing equality predicates for review state, source ID, media type, rating (ALL/UNRATED/EXACT/AT_LEAST), favorite (ALL/FAVORITES/NOT_FAVORITES), exact digest and escaped literal path. Add:

```sql
EXISTS (SELECT 1 FROM asset_tags AS at
        WHERE at.asset_id=assets.asset_id AND at.tag_id=?)
EXISTS (SELECT 1 FROM asset_entities AS ae
        WHERE ae.asset_id=assets.asset_id AND ae.entity_id=?)
```

The schema-6 assignment primary keys and owner indexes support these predicates; `EXISTS` cannot multiply gallery rows. One `compile_query(GalleryQuery)` returns the base `FROM`, `WHERE` SQL, parameter tuple and closed order expression used by **count, first/later pages, stable-ID rank, and detail membership**. Page projection may join source/entry display data only if it still yields one row per asset; preserve existing availability fields and do not add a multiplicative assignment join. Rank uses the same predicate plus target ID and the same tuple order; check the returned asset ID and rank against the current generation before selecting. Detail requires both the captured stable ID/revision and query membership in the same snapshot. No SQL identifiers or order expressions come from user text. Do not materialize a full result or taxonomy list.

## GUI read owner and coherent snapshots

The GUI uses one owned catalog-gateway `QThread`, with one SQLite **read-only** connection created, used and closed on that thread for gallery reads. It opens the catalog in `mode=ro`, checks schema 6, sets `busy_timeout=50` ms, and has a SQLite progress handler that checks a cancellation event and `monotonic` deadline (for example every 1,000 virtual-machine instructions). The GUI does no count, page, rank, detail, picker or gallery-source-filter SQL, including inside `AssetModel.data()`/paint, startup count, selection callbacks, or `refresh()`. Worker replies are plain bounded data delivered by queued Qt signals; only the GUI thread mutates the model, cache and widgets. All GalleryWindow-initiated catalog mutations also dispatch through this serial gateway (inventory below), using the unchanged Core APIs and their existing writer connections **after** the gateway's read transaction ends. `AssetModel.update_state` currently writes on GUI `_db`; its GUI path must instead dispatch its captured asset ID/state as a gateway write. `details_for` currently opens metadata on a separate GUI connection; its GUI path becomes one bounded gateway detail operation. Never use the read-only connection for writes or call `metadata.get_asset_metadata()` from GUI detail paint/selection.

Each read operation uses a short `BEGIN` read transaction and ends it before replying. Since `BEGIN` is deferred, its **first actual catalog SELECT** (for example `SELECT 1 FROM assets LIMIT 1`) establishes the snapshot *before* sampling `PRAGMA data_version`; merely issuing `BEGIN` is insufficient. Count, selected-ID validation and first page share **one** established snapshot. The persistent reader connection records `PRAGMA data_version` inside that transaction and a catalog file identity `(device, inode)` checked before/after the operation. Disposable WAL and rollback-journal experiments confirmed `data_version` remains fixed during an established read transaction and advances on that same connection after another connection commits; generated schema-6 adapter tests are still required. A later page, rank or detail operation similarly establishes a new snapshot **before** comparing the same connection's `data_version` and file identity against the published view token, and either reads under that snapshot or returns **view changed** without emitting rows. The token comprises reader incarnation, file identity, data version, applied generation, predicate/order identity and count. It is meaningful only for that one live connection. An unreadable/replaced catalog or worker restart forces a fresh count+first-page generation; never compare versions from different connections. A change committed after a checked snapshot cannot alter its rows; a subsequent request detects it. Any local mutation request marks the published view/action targets stale **before dispatch**; success or failure requests a fresh generation so old page/rank/detail replies cannot revive targets. No read transaction stays open across user input.

This detects changes that could otherwise pair an old count with a new page/rank. It does **not** promise a static view across edits: previously loaded rows may be shown as the prior view while reloading, but cannot become new command targets by row index. On token mismatch or mutation submission, mark the view stale, disable row actions, clear pending selection/detail, and request a new generation after the write finishes. A captured action uses stable asset ID and existing revision/path drift checks, not the row number. Cached rows may remain visible with a clear prior/stale label while a replacement is pending; missing page results never borrow rows from an older generation. A failed Apply retains the old count/pages only if that old token is still current; an already stale old view stays visibly stale and non-actionable until a successful reload.

`AssetModel.rowCount()` returns only the published count. At startup it returns zero with **loading** state until count plus page zero arrive. `data()` reads only an in-memory 256-row page or returns a non-targetable **Loading page…** placeholder; `AssetRole` is `None` for pending/error rows. `flags()` and every command entry point reject pending/failed/stale rows even if Qt programmatically supplies an index. `asset_at()` on an unresolved GUI row raises a specific pending/stale exception; callers use a nonthrowing loaded-row helper before enabling an action. A later page is requested at most once per generation/page; completion inserts it into the 24-page LRU and emits `dataChanged` for that page only. Rank and detail replies include generation, view token, stable ID and revision; late/mismatched replies are discarded. Detail has its own visible loading/error state and cannot open an action while unresolved. No async completion changes focus or selection. Count/page/rank/detail errors show a read failure or stale-view status, not a successful empty query.

## Rollback-journal concurrency prerequisite

Schema 6 does not enable WAL; default rollback journaling allows a reader's SHARED lock to hold up a writer's commit. A disposable generated SQLite experiment held a read transaction for 350 ms and observed a synchronous writer commit take about 429 ms. That is evidence of a design hazard, not gallery acceptance. The gateway's 50 ms **reader** busy timeout cannot bound a GUI writer's default SQLite wait. Do not change journal mode, schema, durability settings or Core mutation semantics to hide this.

Two approaches were considered. A reader-quiescence lease around each existing GUI writer would cancel the active reader, then defer the GUI callback until the reader finished; it cannot safely run the existing synchronous callback immediately without a GUI wait. Making it safe requires converting every write callback and captured dialog into deferred continuations anyway, plus handling queued reader starts. It leaves synchronous service reads able to overlap a gateway write and it risks new callback ordering gaps. The chosen prerequisite is a **single serial catalog gateway** for this window: it never holds its read transaction while invoking a write, prioritizes a captured write request by canceling the active read, and posts completion to GUI. The mutation's Core function and arguments/results remain unchanged. No GUI mutex, SQLite busy wait or `QThread.wait()` is used. This is a separately reviewable source slice *before* filter controls, not an unreviewed whole-app conversion.

At a write intent, capture stable IDs, revisions, form values and any existing plan/neighbor ID on GUI, refuse a second outstanding mutation visibly, mark the current gallery token stale and row-index actions disabled, then enqueue exactly one write. The worker rolls back/commits its current reader transaction before running the original service call through its **own** existing writer connection; no read request may start until that call returns. Do not cancel a dispatched write or retry it automatically: an opaque service call may commit before reporting or be blocked by the existing scan worker. A queued write may be canceled before dispatch; an active write remains owned through actual completion, including on window close. On success, send the original result to its dialog, refresh relevant lists and request a new gallery generation; on error, surface the original refusal and still reload the gallery before enabling row actions. Never re-read row N to construct a write target after an async delay. This gateway coordinates only GalleryWindow's local UI commands, not external processes, other library windows, scanner jobs or global `FR-LIB-003` multi-instance writers. Scanner/external workers can still write independently; `data_version` detects their commits, and an active Core service call retains its original lock/wait behavior **off GUI**. The two-second gallery-read ceiling does not become a deadline for mutation, metadata-list or source-management service calls.

The prerequisite routes these current **catalog-mutating GUI entrypoints** through the gateway, preserving each API's transaction, revision and refusal rules:

| --- | --- | --- |

WHERE asset_id=? AND revision=?` in the same single-asset SQL/trigger transaction off GUI, with a visible stale-target refusal on zero rows. The current **GalleryWindow/catalog read** call sites also need an async route so a gateway write cannot introduce a new GUI SQLite wait: `AssetModel.__init__`, `_query_count`, `_load_page`, `row_for_asset`, `refresh`, `details_for`, and `data()`; window startup `list_sources`/source-root validation, `refresh_sources`, `_source_selected`, `refresh_source_issues`, `refresh_collections`, `refresh_duplicates`, `open_curation_history`, and `_show_detail`; `MetadataEditor.refresh`/`MetadataTaxonomyPanel.refresh` and their `metadata.get_asset_metadata`/`list_tags`/`list_entities`; `CurationDialog.reload`; `BulkCurationDialog.preview`/`reload`/`refresh_history`/`load_group`; and `GalleryWindow._curate_selected`'s `PrivateSelectionStore` catalog lookup (the separate private database write keeps its existing checks). The external-action settings and original dispatch already run in `ExternalActionWorker`; thumbnail/cache/scan work already owns separate workers. Standalone CLI `AssetModel` and non-GalleryWindow library launcher operations remain explicit non-GUI/synchronous paths.

For the legacy source-management and taxonomy-editing reads, the gateway may invoke the unchanged service read API in a serial **legacy task** and return its result to the GUI; do not claim their result size or duration has the gallery page/picker limits. Their controls show pending/refusal and ignore late replies if the dialog/window closed. This moves catalog I/O off the GUI without changing the content/transactions of `metadata._records()` or `list_sources()`. It does not qualify those panels for 100k responsiveness; an oversized legacy listing may still consume memory on the worker and must not be called by the new bounded filter picker. If this source slice is too broad to review atomically, freeze and review the catalog-gateway/legacy-callback migration as a prerequisite patch before adding any new filter controls. The precise entrypoint inventory above is the review boundary; do not silently add unrelated scanner, external action or metadata backend refactors.

## Request bounds, scheduling and close

Keep 256 rows per gallery page and 24 cached pages. Return at most one first page, one later page, one rank, one detail, one picker page or one source page per new gallery-read request. Cap each gallery text field at 1,024 code points and 4,096 UTF-8 bytes and the serialized row at 8 KiB (at most 2 MiB per page). Use SQL `CASE` with `length(text)` and `length(CAST(text AS BLOB))` guards **in the projection**, including a total projected-text budget, so oversized stored path/source/provenance/label text is replaced with an overflow marker before Python fetch; do not fetch full text and then truncate in Python. An oversized path is **unavailable for command capture**, never silently shortened into a valid path. Cap detail payload at 64 KiB and each provenance/assigned-taxonomy/alias list at 64 entries plus an overflow marker; overflow is a visible detail refusal or explicit incomplete-detail state, never an apparently complete record. Bound picker input to 128 code points, canonical name/alias/category labels to 256 code points and 1,024 UTF-8 bytes each, 64 canonical records per page plus one lookahead row, and 64 source records per page. Oversized labels are shown as unavailable/refused rather than stored as truncated identities. ID-only and numeric count/rank replies have fixed size. New gallery-read requests do no source-media `stat`/scan/thumbnail/cache I/O; unchanged legacy service tasks have their own scope and limits.

Use keyset paging for **new filter pickers** and sources, not an unbounded combo or `metadata._records()`. Normalize picker input exactly like `metadata._name`: NFC, whitespace collapse, casefold, then NFC again; reject controls and enforce the input cap before a request. Search a canonical table in canonical normalized-name/category/ID order with a keyset cursor and `LIMIT 65`, matching its normalized-name prefix or `EXISTS` for a matching normalized alias. This yields at most one canonical row even if several aliases match. The canonical-name and alias columns have schema-6 indexes, but an alias match through a canonical-order `EXISTS` may still scan many canonical rows; **do not claim an indexed end-to-end alias plan** without `EXPLAIN QUERY PLAN` evidence on generated fixtures. The two-second read deadline then refuses with “refine the prefix” rather than materializing all matches. No leading-wildcard alias search or hidden fallback. Exact selected-ID validation is separate from lookup pagination. The existing metadata editor's legacy listing remains an explicitly unqualified existing API task; its result is never reused to populate this picker. Gallery source picker uses only `sources` catalog rows, ID/label/health needed for its filter; no source issue enumeration. Keep a separate scan-target control/state. Changing the gallery source draft never calls `_source_selected()`, `refresh_source_issues()`, `list_sources()` or starts a scan; scan target/status changes never apply a gallery filter. A deleted source ID remains visibly stale rather than silently resetting to All.

Allow one active gateway operation and a bounded pending set: **one latest Apply** (supersedes an older candidate), at most two viewport page keys, one rank, one detail, one taxonomy lookup, one gallery-source lookup, one outstanding mutation, and **four legacy-read requests total** across all dialogs/contexts, with at most one latest request per context. A fifth distinct legacy read refuses visibly as “catalog busy; retry”; replacing an older request from the same context releases its slot. A second mutation refuses visibly rather than replacing an earlier one. A new mutation marks the view stale and cancels an active/queued gallery read before it begins; a new Apply replaces only the pending Apply; picker edits replace only their pending lookup. Mutation has dispatch priority, then Apply, visible page, rank/detail, picker/source, then legacy reads. An already active opaque legacy API call may delay a queued mutation until actual completion; it never blocks GUI. All requests carry generation/request IDs. Cancellation, busy timeout and a proposed **two-second per-operation deadline** apply to the new bounded gallery reads only; they are cooperative refusals, not a universal wall-clock guarantee against a kernel-blocked file operation. A 50 ms busy timeout is similarly a reader design choice, not a responsiveness proof. Existing Core service calls retain their own separate-connection lock behavior and no newly claimed cancellation/deadline/output bound. No unbounded thread creation or GUI-thread fallback is allowed.

Closing rejects new requests, cancels queued/active **read** work and marks replies undeliverable, but never cancels a dispatched mutation or closes the read connection from GUI. Retain the gateway and refuse/ignore `closeEvent` until any active service call actually returns, the worker closes its own read connection and the thread reports `finished`; schedule a retry of close from `finished`. A worker stuck in native I/O or an existing Core service busy wait leaves a visible cleanup-pending refusal and retained ownership. Dialog closure does not discard a dispatched mutation: its result still reaches the window, which invalidates/reloads the gallery before allowing another command, even if the dialog no longer receives UI feedback. Gateway completion joins the existing thumbnail/viewer/external close guards; it must not weaken them. Report actual stopped/retained state in tests and package smoke, without claiming process-wide cleanup.

A is a reviewed infrastructure slice, not a claim that the gallery read gate is already satisfied.

In the same reviewed source slice, adapt `AssetModel`, `GalleryWindow`, `MetadataTaxonomyPanel`, `MetadataEditor`, `CurationDialog`, and `BulkCurationDialog` callbacks in `prototypes/qt/app.py` according to the complete read/write inventory above. Activate A's gateway **only when** count+first page share one established snapshot; later page/rank/detail check the same-connection version/file token; pending/stale rows and actions are non-targetable; SQL projections are bounded; local mutations invalidate before dispatch; the GUI has no catalog read/write path that can wait on the gateway; and actual close ownership is tested. No intermediate async GalleryWindow model may be exposed or shipped.
